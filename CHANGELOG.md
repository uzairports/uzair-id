# Changelog

Все заметные изменения `uzairports/uzair-id`. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/), версии следуют
[семантическому версионированию](https://semver.org/lang/ru/).

## [Unreleased]

### Added

- **`Uzair::markSessionAsLocal()` — парольный вход в гибридной схеме.** `uzair_id`
  заполняется навсегда, поэтому по нему нельзя отличить завершённый SSO-вход от
  собственного парольного входа приложения: пользователь, хоть раз зашедший через SSO,
  больше не мог войти формой — `uzair.token` отказывал ему на любом маршруте. Пометка
  говорит то, чего колонка сказать не может: эту сессию аутентифицировало само
  приложение, и мерить её строкой `oauth_tokens` нельзя. Ставится после собственного
  входа (`Auth::attempt()` мигрирует сессию), живёт столько же, сколько сессия, и
  снимается входом через SSO. Спрашивается только тогда, когда вход не найден, поэтому
  сессии с настоящим SSO-входом обновляют токен как прежде. `Uzair::sessionIsLocal()`
  отвечает, помечена ли текущая сессия.
- **`Uzair::loginUrl()` — адрес входа через SSO.** Маршрут `redirect` носит имя из
  `login_route`, и второго, фиксированного имени у него быть не может: `Route::name()` в
  Laravel дописывает имя, а не заводит алиас. Приложение, оставившее себе собственный
  `login`, вынуждено было помнить настроенное имя во всех шаблонах. Теперь имя резолвится
  здесь, а шаблон спрашивает адрес; имя, которого нет среди зарегистрированных, отвечает
  корнем сайта, а не 500 из `route()`.
- Эндпоинт `POST {prefix}/logout-device/{token}` (`uzair.logoutDevice`) — завершение
  одного конкретного входа аккаунта, не трогая браузер, из которого его завершают.
  Поиск строки ограничен текущим аккаунтом, поэтому чужая возвращает 404, а не отказ;
  завершение собственного входа передаётся в `logout()`, чтобы сессия ушла вместе с ним.
- Команда `uzair:prune` (`php artisan uzair:prune`) — специализированная консольная
  команда очистки устаревших OAuth-токенов с автоматическим отзывом грантов на SSO
  (если включено `revoke_on_prune`).
- Метод `Uzair::resolveUserUsing(?callable $callback)` — хук для кастомизации создания
  или сопоставления модели локального пользователя из профиля Socialite.
- Настройки `logout_endpoint` (`UZAIR_LOGOUT_ENDPOINT`, по умолчанию `/api/v1/oauth/logout`)
  и `user_endpoint` (`UZAIR_USER_ENDPOINT`, по умолчанию `/api/user`) — возможность гибкой
  настройки путей API авторизации провайдера.
- Поддержка распознавания браузера Samsung Internet (`SamsungBrowser`) в методе
  `OauthToken::deviceLabel()`.
- Настройка `revoke_endpoint` (`UZAIR_REVOKE_ENDPOINT`) — адрес RFC 7009 для отзыва
  refresh-токена при завершении входа. Пусто по умолчанию: адрес не угадывается, чтобы
  установка без такого эндпоинта не платила неудачным запросом на каждом выходе.
- Настройка `revoke_on_single_session` (`UZAIR_REVOKE_ON_SINGLE_SESSION`, по умолчанию
  `true`) — отдавать ли гранты SSO, когда `single_session` завершает остальные входы
  аккаунта. Отзыв стоит round-trip на каждый вход, и платит за него тот самый запрос,
  которого ждёт пользователь: аккаунт на десятке устройств выждет десяток таймаутов,
  прежде чем увидит дашборд. Выключается там, где это ожидание реально; входы при этом
  всё равно заканчиваются здесь — строки удаляются, сессии стираются, `uzair.token`
  отказывает им на следующем запросе, — отдаётся только удалённое снятие гранта.
  `EndSessions::__invoke()` принимает это третьим аргументом (`revoke:`).
- `OauthToken::keepAlive()` — отметка о том, что вход всё ещё используется.
- Настройка `revoke_on_prune` (`UZAIR_REVOKE_ON_PRUNE`, по умолчанию `true`) — отдавать
  ли гранты SSO при уборке. Каждая строка стоит запросов отзыва, а уборка может идти по
  тысячам строк; отключается там, где такой объём реален, а гранты истекают сами.
- `EndSessions::surrender()` — отдать грант входа, не трогая строку. Это то, что нужно
  уборке: строку удаляет она сама, а сессию, которую строка называла, хранилище собрало
  задолго до того, как уборка до неё дошла.
- `EndSessions::surrenderAll(iterable $tokens)` — отдать гранты нескольких входов одним
  заходом. `surrender()` дожидается своих отзывов сам, поэтому вызов его в цикле платил
  ожидание за каждую строку; здесь весь чанк уходит на провод вместе и ожидается один раз.
- Настройка `routes.ip_throttle` (`UZAIR_ROUTE_IP_THROTTLE`, по умолчанию `120,1`) —
  потолок бюджета маршрутов на один адрес, отдельный от `routes.throttle`. `null` снимает
  его совсем.

### Removed

- **Эндпоинт `POST {prefix}/logout-all` (`uzair.logoutAll`) и метод контроллера
  `logoutAll()`.** Завершить все входы аккаунта — значит отдать SSO каждый грант по
  очереди, а один запрос не может отвечать за неизвестное заранее количество: аккаунт с
  десятком устройств выждал бы десяток таймаутов отзыва, прежде чем браузер услышал бы
  хоть что-то, и отказ по любому из них не повторялся. Устройства завершаются по одному
  через `uzair.logoutDevice` — из списка входов, который аккаунт и так видит. Уберите
  ссылки на маршрут и его имя из своих шаблонов.

### Changed

- **Резолвинг адреса входа сведён в `Uzair::loginUrl()`.** `uzair.token` разбирал
  `login_route` второй раз — те же три строки и тот же откат на корень сайта, — то есть одно
  решение лежало в двух местах и могло разъехаться. Middleware теперь зовёт общий метод.
  Туда же переехало предупреждение о незарегистрированном имени, и оно пишется один раз на
  процесс: `loginUrl()` может вызываться из шаблона на каждой странице. `flushState()`
  сбрасывает его наравне с предупреждениями про кэш входов и стор блокировок.
- **README: убран устаревший абзац про запросы без сессии.** Там всё ещё было сказано, что
  такому запросу «достаётся последний вход аккаунта», хотя это поведение убрано: чужая
  строка не отдаётся ни для чтения, ни для завершения, а ищется вход с пустым `session_id`.
  Абзацем выше то же самое уже было описано правильно. Добавлено прямое следствие для API:
  без строки с `session_id = null` маршрут под `uzair.token` ответит `401`.
- **README: предупреждение про `email` рядом с тем, что уже было про `password`.** Названы
  все три случая, в которых вход падает, пока с колонки не сняты уникальность и `NOT NULL`.
- **README: описан конфликт имени маршрута `login`.** `/auth/redirect` намеренно называется
  значением `login_route` и потому сталкивается с Breeze, Jetstream, Fortify или собственным
  маршрутом входа: имя занимается дважды, побеждает зарегистрированный позже, и Laravel об
  этом не предупреждает. Описаны оба выхода.
- **В лог неудачного обмена добавлен код ошибки OAuth (`oauth_error`).** Записывался
  только HTTP-статус, а 400 приходит и когда грант больше не признают (вход надо
  делать заново), и когда провайдер не смог прочитать сам запрос
  (`invalid_client`, `invalid_request` — это уже конфигурация). Статус эти случаи
  не различает, а RFC 6749 различает их одним полем тела. Пишется только код:
  `error_description` — это проза провайдера, которая может вернуть запрос обратно
  вместе с учётными данными, и в лог она не попадает.
- **Настройка `login_cache_store` (`UZAIR_LOGIN_CACHE_STORE`) — стор, в котором лежат
  разрешённые входы.** Записи жили там же, где кэширует приложение, и подвинуть их
  отдельно было нельзя. Между тем при `login_cache_ttl > 0` корректность держится
  ровно на том, что `forgetLogin()` виден всем процессам: приложение, кэширующее
  в неразделяемый стор, не имело способа сделать завершение входа общим для всех,
  кроме как переехать всем кэшем. Стор, про который видно, что он не общий (`array`),
  сообщается в лог один раз на процесс — как это уже сделано для `lock_store`.
  Ничего при этом не отклоняется: запись, которую никто не находит, ведёт себя точно
  так же, как `login_cache_ttl` равный нулю. `file` на нескольких серверах отличить
  осмотром нельзя, и он остаётся на операторе и на примечании в конфиге.
- **Провайдер пакета больше не строит менеджер Socialite на каждом запросе.**
  `SocialiteServiceProvider` объявлен отложенным, но `boot()` доставал `Factory` из
  контейнера — и тем самым разворачивал его на каждом запросе, который обслуживало
  приложение, включая подавляющее большинство тех, что никогда не доходят до OAuth.
  Регистрация драйвера ждёт момента, когда менеджер действительно понадобится
  (`callAfterResolving()`), поэтому уже построенный менеджер тоже расширяется.
  Там же: группы публикации (`vendor:publish`) объявляются только в консоли — вне её
  их всё равно не у кого запросить, а каждая строила пути назначения, четыре из них —
  с меткой времени в имени миграции.
- **Завершение нескольких названных входов отдаёт гранты одной пачкой.**
  Callback завершает входы, которые тот же браузер держал до повторного входа, и их
  может быть несколько: `session_id` называет сессию, а не аккаунт. Раньше каждый
  уходил в `EndSessions::end()` по отдельности и ждал свой отзыв — ожидания
  складывались внутри запроса, которого ждёт браузер. Новый `EndSessions::endAll()`
  удаляет строки, стирает названные сессии одним запросом (одна и та же сессия — один
  раз) и отдаёт все гранты вместе; `end()` теперь выражен через него и ведёт себя
  как прежде.
- `OauthToken::forgetLogins()` — забыть разрешённые входы нескольких сессий одним
  обращением к кэшу вместо одного на вход. Это то, чем пользуются массовые пути
  (`single_session`, завершение входов аккаунта) при включённом `login_cache_ttl`.
- **`config/`, `database/` и `lang/` вынесены из `src/` в корень пакета.** `src`
  остаётся корнем PSR-4 и содержит только классы — как в first-party пакетах Laravel.
  Публикуемые файлы, теги публикации и API не изменились; правка нужна только тем,
  кто ссылался на внутренние пути пакета напрямую.
- **`oauth_tokens.session_id` проиндексирован.** Callback ищет вход, который тот же
  браузер держал до повторного входа, по одному только `session_id` — строка может
  принадлежать другому аккаунту (общий компьютер, вторая учётная запись), поэтому
  запрос нельзя ограничить текущим. Уникальная пара `(user_id, session_id)` начинается
  с `user_id`, а индекс нельзя войти с середины, — так что без своего индекса каждый
  вход читал `oauth_tokens` от начала до конца. Таблица держит строку на живой вход,
  то есть скан рос вместе с числом вошедших и был хуже всего ровно в тот час, когда
  все входят. Новые установки получают индекс из `create_oauth_tokens_table`,
  существующие — из `index_oauth_tokens_by_session` в `uzairid-upgrade-migrations`.
- `EndSessions::__invoke()` удаляет строки одним запросом, а не по одной. Это массовый
  путь — у аккаунта может быть сколько угодно входов, — и выполняется он внутри запроса,
  которого кто-то ждёт: при `single_session` внутри самого callback. Там, где отзыв
  грантов отключён (`revoke_on_single_session=false`, `revoke_on_prune=false`), эти
  удаления и составляли всю стоимость вызова.
- **Пакет требует Laravel 13.** Ограничение `illuminate/*` сужено с
  `^11.0|^12.0|^13.0` до `^13.0`. Поддержка 11 и 12 была объявлена, но никогда не
  проверялась и не могла быть проверена: `orchestra/testbench: ^11.2` требует
  `laravel/framework: ^13.23.0` и конфликтует со всем, что ниже, а матрица CI и так
  состояла из одного `13.*`. Обещание, за которым не стоял ни один прогон тестов,
  снято вместо того, чтобы делать вид, что оно выполняется.
- В блоке `single_session` опубликованного конфига описана цена настройки: каждый
  завершаемый вход отдаётся SSO по очереди внутри callback, которого ждёт браузер.
- При завершении входа отдаётся не только access-токен, но и refresh-токен (если
  `revoke_endpoint` задан). Ничто в OAuth не обещает, что снятие access-токена снимает
  выданный вместе с ним refresh-токен, а переживший выход refresh-токен — это путь
  обратно в аккаунт для того, у кого осталась копия. Оба отзыва выполняются независимо,
  так что отказ по одному не отменяет второй.
- Уборка (`model:prune`) отдаёт грант каждой собираемой строки SSO, а не только удаляет
  её. Закрытый браузер не выходит, поэтому без этого его refresh-токен оставался
  действующим и после того, как здесь на него ничто не указывало, — единственный путь,
  на котором вход заканчивался с живым грантом. Отказ SSO пишется в лог и не мешает
  строке уйти.
- `uzair.token` продлевает строку входа, пока браузер продолжает ходить с запросами
  (не чаще одного раза за половину `session.lifetime`), и передаёт найденный вход
  модели пользователя, так что `currentToken()` в контроллере или во view больше не
  делает второй такой же запрос.

### Fixed

- **Смена id сессии выбрасывала пользователя из приложения.** Вход привязан к
  `session_id`, а `$request->session()->regenerate()` — обычное дело в Laravel:
  подтверждение пароля, второй фактор, `logoutOtherDevices()`. Payload сохраняется, id
  меняется — и следующий же запрос не находил входа для своей сессии, сбрасывал её и
  отправлял залогиненного пользователя обратно в SSO, а строка оставалась висеть с
  грантом, который никто не сдаст до уборки. Теперь сессия помнит, под каким id записан
  её вход (`Uzair::rememberSession()`), и вход переезжает на новый id вместе с браузером
  (`Uzair::followRegeneratedSession()`, `OauthToken::followSession()`). Переезд ограничен
  аккаунтом, за который сессия залогинена: id называет сессию, а не владельца. Сверяются
  с пометкой и `logout`, и `logout-device` — `uzair.token` на них не висит, а выход
  обязан найти вход, чтобы сдать его грант.
- **Гранты уходили в payload очереди открытым текстом.** `UzairAuthenticated` несёт
  `Laravel\Socialite\Two\User`, а `SerializesModels` подменяет идентификаторами только
  модели — поэтому слушатель с `ShouldQueue` записывал в Redis или в `jobs` и access-, и
  ротируемый refresh-токен рядом с `$token`, ради которого пакет держит
  `encrypted`-каст. В payload уходит копия профиля без грантов; объект в текущем запросе
  не трогается, поэтому синхронный слушатель видит его как прежде. Очереди грант нужно
  читать из `$event->token`.
- **`currentToken()` не отдавал вход, выданный вне браузера.** `HasUzairToken` отказывал
  запросу без сессии, и это было верно ровно до тех пор, пока такому запросу доставался
  чужой браузерный вход: отказ был единственным, что удерживало метод от выдачи чужой
  строки. Middleware давно ищет `whereNull('session_id')` — строку самого вызывающего, —
  а трейт продолжал отвечать null на вход, который middleware только что проверил. По
  README для API-маршрутов такую строку и надо заводить, то есть поддерживаемого способа
  прочитать её токен не было вовсе. Теперь запрос без сессии отвечается своей строкой,
  а middleware передаёт найденное в модель на обеих ветках, а не только на браузерной.
  `rememberCurrentToken()` принимает `?string` — приложение, переопределявшее метод с
  `string`, должно расширить сигнатуру.
- **`@property string|null $uzair_id` объявлен на трейте.** Колонку добавляет миграция
  пакета, читает её сам трейт, но статический анализ в хост-приложении сообщал об
  обращении к несуществующему свойству. В корневом проекте это давало шесть ошибок
  PHPStan и красный `composer analyse:all`.
- **`default_token_ttl` не применялся при первичном входе.** `expiresAt()` записывал
  неизвестный срок как null, а middleware читает такое как «просрочено» — поэтому
  провайдер, не присылающий `expires_in`, получал обмен токена на первом же запросе после
  каждого входа. Обмен тратит ротируемый refresh-токен и приходит ровно к тому же
  fallback, который `RefreshAccessToken` применял всегда. Теперь настройка действует на
  обоих путях, и `expires_in`, равный нулю, тоже считается отсутствующим ответом, а не
  сроком «прямо сейчас». Fallback, равный нулю, по-прежнему оставляет срок неизвестным.
- **`logout-device` отвечал гостю 404 вместо 401.** Сплошной 404 стоит там, чтобы аккаунт
  не мог перебором узнать чужие id, но это про вошедшего пользователя: гость из 401 не
  узнаёт ничего нового, а API-клиент с истёкшей сессией из 404 не понимает, что надо
  аутентифицироваться заново. Соседний `logout()` гостя обрабатывал мягко всегда.
- **Захваченное имя маршрута входа теперь сообщается.** Два маршрута могут носить одно имя,
  и Laravel об этом молчит — в списке имён остаётся зарегистрированный последним. Обе
  развязки тихие и выглядят как ошибка в другом месте: выигрывает пакет — гость вместо
  формы входа приложения улетает в SSO; выигрывает приложение — `login_route` и
  `Uzair::loginUrl()` ведут на эту же форму, и кнопка «Войти через SSO» замыкается на
  страницу, с которой её нажали. `Uzair::routes()` считает в конце загрузки все маршруты с
  этим именем, кроме собственных, и пишет предупреждение. Ничего не отклоняется.

- **Уборка удаляла входы, выданные вне браузера, по сроку жизни сессии.** `prunable()`
  мерил все строки одной меркой — «сессия за ней давно истекла в хранилище», — тогда как у
  строки с `session_id = null` никакой сессии нет: `session_id` нулевой ровно затем, чтобы
  вход мог принадлежать API-клиенту или консольной команде. На настройках по умолчанию это
  означало, что интеграция, к которой не обращались четыре часа, удалялась вместе со сдачей
  гранта — учётные данные, стёртые за то, что их не дёргали ночью. Теперь такие входы
  меряются тем, можно ли с ними что-то сделать: удаляются только те, где нет refresh-токена
  и access-токен уже истёк. Пока refresh-токен есть, вход продлевается сколько угодно и
  завершается намеренно — через `uzair.logoutDevice` или `EndSessions`. Правило для строк с
  сессией не изменилось.
- **Ещё две миграции тега `uzairid-user-migrations` предполагали таблицу `users`.**
  `relax_email_column_on_users_table` и `remove_password_column_from_users_table` остались с
  зашитым именем после того, как `add_uzair_id_to_users_table` перевели на модель.
  Приложение, хранящее пользователей в `members` или `staff`, публиковало тег и роняло весь
  `migrate`. Теперь обе читают `config('auth.providers.users.model')`; таблицы, которой ещё
  нет, и таблицы без колонки `email` они не трогают.

- **Миграция `add_uzair_id_to_users_table` предполагала таблицу `users` и ключ `id`.**
  Соседняя `create_oauth_tokens_table` давно читает модель из
  `config('auth.providers.users.model')`, а эта — нет: имя таблицы было зашито, а
  `after('id')` на MySQL попадает в сам запрос, поэтому модель с любым другим ключом роняла
  `php artisan migrate` ошибкой 1054 (на SQLite и PostgreSQL модификатор игнорируется, и
  проблема не проявлялась). Теперь и таблица, и колонка ключа читаются с модели, позиция
  указывается только если такая колонка действительно есть, а таблицы пользователей,
  которой ещё нет, миграция просто не трогает.
- **Отказ базы при записи аккаунта не поддавался диагностике.** Стандартная таблица `users`
  отклоняет SSO-вход дважды: `password` — `NOT NULL` без значения по умолчанию, а писать
  туда нечего, и `email` — уникальный и обязательный, тогда как провайдер не обещает адрес
  и допускает его повторение. Отказ уходил в общий обработчик handshake, который пишет
  только класс исключения, а пользователь видел «authentication failed» — связать это с
  колонкой было не по чему. Теперь `QueryException` при записи аккаунта проходит через
  отдельную строку `error` с именем таблицы, списком колонок без значения по умолчанию,
  признаком уникальности `email` и командой публикации нужных миграций. Схема читается, а
  не разбирается текст ошибки драйвера: три драйвера формулируют эти два отказа
  по-разному, а таблица отвечает одинаково.

- **Отказ хранилища блокировок давал 500 вместо 503.** Перехватывался только
  `LockTimeoutException`, а сбой самого `acquire()` — упавший Redis, `lock_store`,
  не называющий ничего, — выходил наружу: middleware поднимал 500 на каждом запросе с
  истекающим токеном. Ровно та ситуация, которую этот класс отказывается допускать для
  недоступного провайдера и от которой уже защищены все остальные его обращения к кешу.
  Теперь ответ тот же, что и при ожидании лока: `answerWithoutCalling()` принимает вход,
  если его обновил другой процесс, сообщает об удалённом и иначе отвечает 503 — но
  refresh-токен не тратит. Обмен без лока здесь был бы худшим прочтением аварии: пока
  хранилище лежит, лока не держит никто, и все процессы потратили бы один и тот же
  ротируемый токен.
  Взятие лока, работа под ним и освобождение разведены: `exchange()` больше не передаётся
  в `block()` колбэком, иначе один `catch` видел бы и то и другое, и вход, который не
  удалось сохранить, отвечался бы как икота кеша. Освобождение сообщается в лог и не
  поднимается — из `finally` оно перекрыло бы либо успешно сохранённое обновление, либо
  настоящую ошибку обмена; лок истечёт сам.
- **Отказ обновления профиля существующего пользователя игнорировался.** `save()` в
  `ResolveUserFromSocialite` возвращал false при отклонении слушателем `saving`, и этот
  ответ терялся: вызывающий получал модель с именем, которого нет в базе и не будет.
  Теперь это пишется в лог, а атрибуты возвращаются к сохранённым. Вход при этом не
  отклоняется — аккаунт в любом случае тот самый, устаревают только имя и адрес, а
  приложение, чей слушатель отказывает в записи профиля, просит оставить сохранённый
  профиль, а не запретить всем вход. Жёсткий отказ остался там, где аккаунта в базе
  действительно нет: `UzairAuthController::writeAccount()`.
- **Откат апгрейд-миграций ломал схему, которую они не создавали.** `up()` у
  `add_session_id_to_oauth_tokens_table` и `make_oauth_tokens_per_session` пропускает
  таблицу, уже имеющую нужную форму, а `down()` этого не делал — и на установке, где обе
  миграции ничего не изменили, `migrate:rollback` удалял `ip_address` и `user_agent`
  вместе со списком устройств, менял уникальность пары обратно на `unique(user_id)` и
  затем сносил `session_id`. Всё это — структура из create-миграции.
  Теперь `down()` откатывает только то, про что может доказать, что делал сам:
  `make_oauth_tokens_per_session` даёт своей паре собственное имя
  (`uzairid_session_pair_upgrade_unique`) и без него не трогает ничего, включая столбцы,
  а `add_session_id_to_oauth_tokens_table` не удаляет столбец, пока на нём построен хоть
  один индекс. Это тот же приём, которым уже пользовались две индексные апгрейд-миграции.
  Откат настоящей legacy-таблицы работает по-прежнему. Опубликованные в приложение копии
  нужно обновить вручную: `vendor:publish` пишет файл с новой меткой времени, а не
  перезаписывает старый.
- **Отказ `save()` при записи входа игнорировался.** `save()` возвращает false, а не
  бросает, когда слушатель `saving` или `creating` отклоняет запись, и этот ответ
  выбрасывался. Дальше handshake шёл как успешный: браузер оставался входящим против
  строки, которой нет (или против строки со старыми грантами), только что выданные гранты
  никто не отзывал, `UzairAuthenticated` рассылался с несуществующей моделью, а при
  `single_session` следующий за этим проход завершал все остальные входы аккаунта ради
  входа, который не был записан. На следующем же запросе `uzair.token` отказывал браузеру
  и отправлял его входить заново — то есть цикл, оставляющий живой грант на каждом
  проходе. Теперь отказ записи — это ошибка handshake: она уходит в ту же очистку, что и
  любой другой сбой, — сессия снимается, гранты сдаются. Аккаунт проверяется так же:
  `writeAccount()` требует, чтобы разрешённая модель действительно существовала в базе.
- **Отказ приложению читался как отказ входу и разлогинивал всех.** `invalid_client` и
  `unauthorized_client` считались отклонённым грантом, а это отказ клиенту, а не гранту:
  RFC 6749 §5.2 различает их прямо, и ответ будет один и тот же для каждого аккаунта,
  потому что учётные данные за всеми входами одни. Ошибка в `client_secret` возвращала
  `false`, middleware завершал вход — и войти заново было нельзя, новый вход тратит те же
  учётные данные. Теперь такой ответ уходит в `refuseTheClient()`: строка ошибки в лог с
  `client_id` и 503, вход остаётся на месте, гранты не отдаются. Провайдер при этом не
  записывается недоступным — он ответил, и пауза в вызовах лишь отложила бы ту самую
  строку лога. Ответ 401 без читаемого тела по-прежнему считается отклонённым грантом.
- **Недоступный кеш входов отвечал 500 на каждый запрос.** При `login_cache_ttl > 0`
  исключения стора выходили наружу из `cachedLogin()` и `cacheLogin()` прямо в middleware,
  так что упавший Redis ронял всё приложение — оптимизация, включённая ради экономии
  одного запроса. Теперь стор, который не отвечает, сообщается один раз на процесс, а
  вход читается из строки: ровно то, что делает `login_cache_ttl` равный нулю.
  `forgetLogin()` и `forgetLogins()` тоже не поднимают ошибку — строки к этому моменту уже
  удалены, и завершение входа обязано дойти до отзыва грантов; устройство всё равно
  получает отказ на следующем запросе.
- **Неудавшийся callback оставлял выданные гранты живыми.** Код авторизации обменян
  раньше, чем что-либо в `callback()` может упасть, а строка при падении не пишется — так
  что access- и refresh-токены оставались признанными на UzAirports ID до собственного
  истечения: строки, которую мог бы завершить пользователь, нет, и уборке `model:prune`
  находить нечего. Теперь они отдаются провайдером тут же, как это уже делает
  `RefreshAccessToken`, когда не может сохранить только что выданное. Обе половины
  закрыты: `UzairportsProvider::user()` переопределён и сдаёт гранты, если не удался
  запрос профиля — обмен идёт первым, и на этом шаге токены живут только локальной
  переменной внутри `user()`, наружу метод отдаёт исключение, — а контроллер сдаёт всё,
  что падает после `Auth::login()`. Общая точка — `EndSessions::surrenderIssued()`.
- **Профиль принимался без проверки HTTP-статуса.** `getUserByToken()` смотрел только на
  то, разобрался ли JSON, тогда как обмен токена рядом (`decodeTokenResponse()`) статус
  проверял всегда. Запросы идут с `ALLOW_REDIRECTS => false`, поэтому 302 возвращается
  обычным ответом и Guzzle по нему ничего не поднимает: шлюз перед провайдером,
  ответивший редиректом со своим телом, превращался в пользователя и входил. Ответы 4xx
  и 5xx проходили тем же путём, если приложение выключило `http_errors` через
  `uzairports.guzzle`. Теперь требуется 2xx, и отказ по статусу сообщается отдельно от
  отказа по телу.
- **Привязка по email могла объединить две SSO-личности в один аккаунт.** При
  `link_by_email = true` поиск непривязанной записи и запись `uzair_id` в неё — два
  разных запроса, а уникальный индекс второго писателя не отклоняет: строка одна и та же,
  и второй записью просто перезаписывает первую. Две личности оказывались в одном
  локальном аккаунте. Теперь привязка условна (`where uzair_id is null`), и проигравший
  берёт новый аккаунт — адрес, про который провайдер не обещал, что он подтверждён, не
  повод отнимать запись у того, кто успел раньше.
- **Вход, который `uzair.token` больше не мог продлить, удалялся, но грант не
  отдавался.** Обмен отклоняется по refresh-токену, а лежащий рядом access-токен
  действителен ещё до `refresh_leeway` секунд; строка удалялась напрямую, и после
  этого на него уже ничто не указывало — сдать его было некому. Теперь завершение
  идёт через `EndSessions::end()`, как и все остальные завершения в пакете: оба
  гранта уходят провайдеру, а строку, которую другой запрос уже удалил, действие
  находит удалённой и ничего не отзывает по устаревшему снимку. Конструктор
  `EnsureAccessTokenIsFresh` принимает вторым аргументом `EndSessions`.
- **Конфиг отсылал к удалённому эндпоинту.** Блок `single_session` советовал тем, кому
  нужно завершить остальные входы, воспользоваться «sign-out everywhere», хотя
  `logout-all` в этом же релизе и удалён, а `Uzair::routes()` прямо утверждает
  обратное. Конфиг публикуется в хост-приложение через `vendor:publish`, поэтому
  интегратор читал именно неверную версию. Тот же призрак убран из докблока
  `EnsureAccessTokenIsFresh`.
- **Прунинг мог удалить действующий вход.** `updated_at` писался только при обновлении
  токена, поэтому вход с access-токеном, живущим дольше окна прунинга (например,
  восьмичасовой токен при `session.lifetime=120`), оставался нетронутым, пока владелец
  работал, — и `model:prune` удалял его, после чего пользователя выбрасывало из
  приложения. Теперь `updated_at` означает «когда браузер приходил в последний раз».
- `currentToken()` не кешировал отрицательный ответ: сессия без входа приводила к
  запросу в базу при каждом обращении.
- **Сохранённый email затирался, если SSO его не прислал.** Имя в такой ситуации
  оставалось прежним, а адрес перезаписывался на `null`, хотя почта на стороне
  провайдера необязательна и вход без неё не означает, что её отозвали. Теперь
  сохранённое значение остаётся на месте; изменившийся адрес по-прежнему записывается.
- **Запрос без сессии мог завершить чужой вход.** Такому запросу — API-клиенту,
  консольной команде — доставался последний вход аккаунта, и если продлить токен не
  удавалось, строка удалялась: устройство, которое этот запрос не делало, выбрасывало из
  приложения. Отказ запросу остался, удаление строки — только для той сессии, которой
  она принадлежит.
- В документации по уборке `model:prune` вызывался без `--model`. Команда ищет модели
  только в `app/Models` приложения, поэтому `OauthToken` в неё не попадал и уборка
  молча не делала ничего.
- **Отказ в refresh-токене вызывал 503 вместо редиректа на повторный вход.** Метод
  `RefreshAccessToken::grantWasRejected` теперь распознаёт HTTP 401 и коды OAuth 2.0
  (`invalid_grant`, `invalid_token`), предотвращая циклическую ошибку недоступности
  сервиса при отозванном или просроченном токене.
- **Предыдущий вход не очищался при смене пользователя в том же браузере.** Метод
  `endPreviousLogin` в контроллере теперь удаляет запись предыдущей сессии браузера
  независимо от того, принадлежала ли она тому же `user_id`.
- **`EndSessions` не удалял сессии по `session_id` завершаемых токенов.** Метод
  `deleteStoredSessions` теперь удаляет записи из таблицы сессий базы данных как по
  `user_id`, так и по собранным `session_id` токенов.
- Удалён пустой каталог `src/Jobs`.
- **Уборка отзывала гранты по одному и занимала часы вместо минут.** Трейт `Prunable`
  подметает по модели за раз, а `pruning()` дожидался отзывов своей строки прежде, чем
  прочитать следующую, — каждая строка стоила собственного таймаута отзыва, и уборка
  тысяч строк шла как их сумма. Единственным выходом было `revoke_on_prune=false`, то
  есть оставить живые гранты. `OauthToken::pruneAll()` переопределён: гранты чанка
  уходят одним `surrenderAll()` и ожидаются один раз, строки по-прежнему удаляются
  поштучно (события модели срабатывают), а строка, которая не удалилась, репортится и не
  оставляет остальной завал на месте. `pruning()` остался хуком для одиночного `prune()`
  и в уборке больше не участвует, чтобы один и тот же грант не отзывался дважды.
- **Уборка не забывала закешированные входы.** При `login_cache_ttl > 0` подметённая
  строка продолжала отвечать за себя из кеша, пока запись не истечёт, — устройство всё
  это время пускали дальше. Теперь чанк сбрасывает записи всех осиротевших сессий одним
  вызовом `forgetLogins()`.
- **Лимит на маршрутах обходился ротацией session-куки.** Браузер определялся по куке,
  которую пишет сам вызывающий, поэтому клиент с новым `session_id` на каждом запросе
  каждый раз попадал в новое ведро, а потолок на адрес был выставлен как
  `attempts * 10` — на дефолтах это 600 запросов в минуту на эндпоинты, которые пишут в
  базу и ходят к провайдеру. Потолок вынесен в собственную настройку `routes.ip_throttle`
  со своим значением, так что поднятие бюджета браузера больше не поднимает тихо
  разрешённое адресу в десять раз. Ключи двух лимитов разведены (`ip:` и `address:`),
  чтобы запрос без куки не тратил одно ведро дважды.
- **`Auth::login()` вызывался внутри транзакции.** Событие `Login` и всё, что на него
  навешано в хост-приложении, срабатывало до коммита: листенер, ставящий задачу в
  очередь, отдавал воркеру имя ещё не существующей строки, а читающий через второе
  соединение не видел аккаунта вовсе. Оборачивать чужие листенеры в транзакцию, которую
  открыл пакет, — не его решение. Теперь `storeIdentity()` пишет аккаунт (своя
  транзакция), затем логинит браузер, затем пишет строку входа под уже устоявшийся
  `session_id`; каждая запись атомарна сама по себе и по-прежнему повторяется один раз
  при нарушении уникального индекса. Отдано за это откат аккаунта при неудачной записи
  токена: строка остаётся, аккаунт остаётся связанным — что следующей попытке и нужно, —
  а браузер разлогинивается как и раньше.
- **Запрос без сессии одалживал вход браузера.** `EnsureAccessTokenIsFresh` подбирал
  такому запросу — API-клиенту, консольной команде — последний вход аккаунта, то есть
  строку чужого браузера, и дальше отмечал её как живую на каждом вызове: брошенный вход
  никогда не доходил до `prunable()`, а значит его грант никогда не отдавался SSO.
  Вдобавок запрос тратил ротируемый refresh-токен того браузера, чтобы обновить токен,
  который ему всё равно нечем прочитать — `currentToken()` без сессии отвечает `null`.
  Теперь такой запрос ищется по `session_id IS NULL`: колонка нулевая ровно затем, чтобы
  вход мог быть выдан вне сессии, и это его собственная строка. Как следствие удаление
  непродлеваемого входа больше не нуждается в оговорке про чужую строку.
- **Лок вокруг обмена refresh-токена мог не быть локом.** `lock_store` по умолчанию
  `null`, то есть берётся то, чем кеширует приложение: хранилище без атомарных локов
  отвечало на вызов фатальной ошибкой вместо лока (настройка кеша выкидывала
  пользователя), а хранилище в памяти одного процесса — локом, которого не видит ни один
  другой процесс, и молчало об этом, хотя ротируемый токен там может быть потрачен
  дважды. Оба случая теперь называются в логе — один раз на процесс, — а обмен идёт без
  лока вместо срыва входа. Требование к разделяемому хранилищу проговорено в комментарии
  к `lock_store`.
